---
title: Multi-instance deployments
description: Separate API and worker roles and coordinate multiple Teldrive processes safely through PostgreSQL.
---

A single Teldrive process is the recommended default. Move to multiple instances only when you have a measured availability or capacity requirement.

## Shared state

Every instance in the same deployment must use the same:

- PostgreSQL database and schema;
- `security.signing-key`;
- `security.data-key`;
- content-encryption key map and active-key policy;
- Telegram application identity appropriate for the deployment.

If different instances use different data keys, a request or background job can land on a process that cannot decrypt credentials or encrypted job arguments created by another process.

## API + worker on every instance

The default is:

```yaml
jobs:
  run-workers: true
```

With two Teldrive processes, both can serve HTTP and both can consume River jobs from the shared PostgreSQL database.

This is the simplest horizontally scaled shape, but account for the combined PostgreSQL connection pools and Telegram concurrency.

## Dedicated API instances

Disable workers on API-only processes:

```yaml
jobs:
  run-workers: false
```

or:

```bash
TELDRIVE_JOBS_RUN_WORKERS=false
```

Then run at least one separate process with workers enabled.

Example topology:

```text
                 ┌──────────── API 1 (workers off)
load balancer ───┼──────────── API 2 (workers off)
                 │
                 └──────────── Worker (workers on)
                               │
                               ▼
                         shared PostgreSQL
```

A worker process is still the same Teldrive binary. The `run-workers` setting controls whether it consumes background jobs; it does not create a separate worker executable.

## Database pool budgeting

Each process owns its own PostgreSQL pool. If three processes each allow 25 connections, the potential application total is much larger than 25.

Before scaling, set per-process values intentionally:

```yaml
database:
  max-connections: 10
  min-connections: 1
```

The correct values depend on request volume, worker load, PostgreSQL capacity, and the number of instances.

## Bot rotation

For a single instance:

```yaml
telegram:
  bot-rotation-backend: memory
```

For multiple instances that must coordinate download-bot rotation:

```yaml
telegram:
  bot-rotation-backend: database
```

The database backend exists specifically for cluster-wide coordination.

## Event connections

`events.max-connections-per-user` is enforced per API instance. With a load balancer, the overall number of event connections for one user can therefore exceed the per-instance value.

Make sure the load balancer and reverse proxy support long-lived SSE connections across all API instances.

## Shared cryptographic configuration

Use one secret source and distribute the same versions to all processes:

```yaml
encryption:
  active-key-version: 2
  keys:
    1: OLD_KEY
    2: CURRENT_KEY
```

Deploying a new active content key is safer as an ordered rollout:

1. distribute the new key version to **all** instances while leaving the old version active;
2. verify all instances can start;
3. switch the active version everywhere;
4. keep old versions available for old files.

## Rolling upgrades

Because startup may run database migrations, read release notes and back up PostgreSQL before rolling out a new version.

Do not assume arbitrary old and new versions can always operate against the same schema during a prolonged mixed-version rollout.

For a small self-hosted deployment, short maintenance windows are often simpler and safer than building a complex zero-downtime upgrade system.

## When not to scale horizontally

Multiple instances will not fix:

- a Telegram-side rate limit;
- a single client's slow network;
- an incorrectly buffering reverse proxy;
- CPU spent hashing on the same constrained host;
- an undersized PostgreSQL server;
- bad concurrency settings.

Measure the actual bottleneck first. Vertical scaling and correct tuning are frequently enough.
