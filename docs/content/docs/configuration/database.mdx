PostgreSQL is the durable control plane for Teldrive. Telegram stores file payloads; PostgreSQL stores the metadata and application state needed to find, authenticate, organize, share, and process those files.

## Basic configuration

```yaml
database:
  schema: teldrive
  url: postgres://teldrive:password@127.0.0.1:5432/teldrive?sslmode=disable
  application-name: teldrive-v2
  max-connections: 25
  min-connections: 2
  max-connection-idle: 5m
  max-connection-life: 30m
  health-check-interval: 30s
  connect-timeout: 10s
  auto-migrate-legacy: true
```

The database URL is required.

## Schema

The default PostgreSQL schema is:

```text
teldrive
```

Teldrive uses this schema for application tables and its River/RiverPro job infrastructure. The schema name must be a valid PostgreSQL identifier.

Using a separate schema is useful when a database is shared with other applications:

```yaml
database:
  schema: my_teldrive
```

Keep the schema name stable after deployment unless you are deliberately performing a database migration.

## Migrations

At application initialization Teldrive runs the required Teldrive, River, and RiverPro migrations before it opens the long-lived application pool.

For a normal installation, you do not run SQL migration files manually.

A safe upgrade workflow is still:

1. back up PostgreSQL;
2. update the Teldrive image or binary;
3. run `teldrive check` against the new version;
4. start the application;
5. inspect logs before declaring the upgrade complete.

## Legacy migration

```yaml
database:
  auto-migrate-legacy: true
```

When enabled, startup can detect and migrate a legacy Teldrive database before applying the current v2 schema.

For important installations, take a full database backup before the first v2 startup. Automatic migration is convenient, but a tested backup is what gives you a rollback path.

## Connection pool

Defaults:

| Setting | Default |
| --- | ---: |
| `max-connections` | `25` |
| `min-connections` | `2` |
| `max-connection-idle` | `5m` |
| `max-connection-life` | `30m` |
| `health-check-interval` | `30s` |
| `connect-timeout` | `10s` |

Do not multiply `max-connections` blindly when scaling Teldrive horizontally. A four-instance deployment with `25` maximum connections per instance can consume roughly four times the database connection budget.

Plan the total across:

```text
API instances
+ worker instances
+ administration tools
+ backup/monitoring clients
+ safety headroom
```

## TLS

For PostgreSQL on the same private host or an isolated container network, `sslmode=disable` is common.

For remote or managed PostgreSQL, use the TLS mode and certificate settings required by your provider. Do not copy the local quick-start URL to a database reached over an untrusted network.

## Backups

A basic logical backup:

```bash
pg_dump --format=custom --file=teldrive.dump 'postgres://teldrive:password@localhost:5432/teldrive'
```

Restore to an isolated test database periodically. A backup you have never restored is only an assumption.

Remember that encrypted Telegram credentials in the database also require the matching `security.data-key`. Back up that key independently.

## What failure looks like

If Teldrive cannot reach PostgreSQL during startup, it fails initialization rather than serving a partially functional application. Check:

- hostname and port;
- database/user names;
- password escaping in the URL;
- TLS mode;
- firewall/container network;
- PostgreSQL readiness;
- connection limits.

Use `teldrive check` as the quickest configuration-and-dependency validation command.
