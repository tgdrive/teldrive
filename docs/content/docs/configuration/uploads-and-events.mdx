title: Uploads and events
description: Configure resumable upload sessions, hashing, local imports, background workers, and live UI events.
---

These settings mostly affect large-file workflows and the live web interface. The defaults are suitable for a single normal server.

## Upload sessions

```yaml
uploads:
  session-ttl: 168h
  hashing-enabled: true
  local-import-roots: []
```

### `session-ttl`

Default `168h` means resumable upload sessions live for seven days. This gives interrupted large uploads time to resume without keeping abandoned sessions indefinitely.

### `hashing-enabled`

When enabled, Teldrive computes and stores BLAKE3 hashes during uploads.

```yaml
uploads:
  hashing-enabled: true
```

Disable automatic hashing only when you have measured the CPU/I/O cost and do not need server-computed hashes:

```yaml
uploads:
  hashing-enabled: false
```

Client-supplied checksums still require verification when provided.

## Local background imports

By default:

```yaml
uploads:
  local-import-roots: []
```

An empty list disables local server-side imports. To allow imports from a server directory:

```yaml
uploads:
  local-import-roots:
    - /srv/imports
    - /mnt/media
```

Every configured root must be an **absolute path**.

For containers, mount the path into the Teldrive container at the same path you configure, preferably read-only if Teldrive only needs to ingest it.

```yaml
volumes:
  - /srv/imports:/srv/imports:ro
```

Do not expose arbitrary host directories as import roots. This setting defines which server-side files Teldrive is allowed to read for import jobs.

## Background jobs

Teldrive uses River/RiverPro for background work.

```yaml
jobs:
  run-workers: true
```

The default is `true`, so a normal all-in-one Teldrive process serves the API and executes background jobs.

For advanced multi-instance deployments you can separate API and worker roles by running instances with different values. See [Multi-instance deployments](/advanced/multi-instance).

Environment variable:

```bash
TELDRIVE_JOBS_RUN_WORKERS=false
```

## Live events

The web UI receives replayable application events over Server-Sent Events (SSE).

Defaults:

```yaml
events:
  batch-size: 100
  max-connections-per-user: 5
  heartbeat: 20s
  write-timeout: 10s
  ticket-ttl: 2m
  retention: 168h
  cleanup-interval: 1h
  connect-timeout: 10s
  ping-interval: 5s
  reconnect-min: 100ms
  reconnect-max: 30s
```

### Reverse proxy requirements

Your reverse proxy must allow long-lived HTTP responses for SSE. Avoid buffering the event stream and make proxy timeouts comfortably longer than the heartbeat interval.

If ordinary pages load but upload/task status never updates until refresh, investigate the SSE path and proxy buffering first.

### Connection limits

`max-connections-per-user` is enforced per API instance. In a horizontally scaled deployment, the effective system-wide number can be higher because each instance has its own limit.

### Event retention

The default `168h` retains replayable events for seven days. Longer retention increases the amount of event history PostgreSQL must keep. Change it only when you have a concrete replay/recovery requirement.

## HTTP transfer timeouts

Large uploads and downloads are also affected by:

```yaml
http:
  read-timeout: 1h
  write-timeout: 1h
```

and by any timeout imposed by your reverse proxy, CDN, load balancer, or client.

When a transfer consistently dies at the same wall-clock duration, compare every layer's timeout before changing Telegram concurrency settings.
